# API Key Management Workshop Features

## Purpose

API key management gives approved client applications scoped, auditable access to FMT REST endpoints without sharing database access or long-lived unmanaged secrets. The feature separates internal approval from client-side key claiming, stores only hashes of secrets, and enforces endpoint scopes at runtime.

This document reframes the completed API-key implementation as workshop feature slices for product, security, and engineering discussion.

## Feature Slices

### 1. API Client Registration

Purpose: Register each consuming application or organization as an API client before any keys can be issued.

User benefit: Admins can manage access by client instead of by anonymous credentials. This makes ownership, contact information, and lifecycle decisions easier to review.

Endpoint and security impact:

- Admin JSON routes support creating, listing, viewing, enabling, and disabling API clients.
- Admin UI routes support creating and viewing clients.
- API keys associated with disabled clients must not authenticate.
- API keys cannot authorize admin client-management routes.

Current implementation status: Implemented with `api_clients`, API-client DTOs, EntityManager repository access, service workflow, JSON resources, admin UI support, and backend tests.

### 2. Claim Invitation Provisioning

Purpose: Let an internal admin pre-approve one future API key for a client by setting the claim identifier, key name, environment, scopes, expiration, and approval reference.

User benefit: Client access is approved before a secret exists. The client-side admin can only claim what was already approved and cannot expand scope during claim.

Endpoint and security impact:

- Admin JSON route creates claim invitations for a client.
- Admin UI route creates claim invitations and shows the raw claim code once.
- Claim codes are generated by the system and manually delivered out-of-band.
- Only a BCrypt hash of the claim code is stored.

Current implementation status: Implemented with claim-invitation model, scopes on invitations, BCrypt claim-code hashing, one-time raw claim-code response, audit events, admin JSON routes, admin Qute pages, and tests.

### 3. Client Claim Workflow

Purpose: Let a client-side admin exchange an approved claim identifier and one-time claim code for a raw API key.

User benefit: The client gets a full API key only after proving possession of the approved claim information. The raw API key is displayed once so the client can store it in its own secret manager.

Endpoint and security impact:

- JSON claim endpoint remains available at `POST /api/v1/api-keys/claim`.
- Qute claim UI supports a three-step flow: enter claim information, review approved access, complete claim.
- Successful claim generates the API key, persists only prefix and HMAC hash, marks the invitation claimed, and prevents reuse.
- Failed claim-code attempts are counted and can lock an invitation.

Current implementation status: Implemented with claim DTOs, claim service workflow, review-without-consuming support for the UI, JSON claim route, Qute claim screens, one-time raw API-key display, and tests.

### 4. API-Key Authentication For Endpoints

Purpose: Authenticate normal API requests with `X-API-Key` and reject invalid, expired, revoked, rotated, or malformed keys.

User benefit: Client applications have a clear, stable authentication mechanism for machine-to-machine API access.

Endpoint and security impact:

- Normal API requests send `X-API-Key: <full-api-key>`.
- Key format is `ak*{env}*{publicId}.{secret}`.
- The stored key prefix supports lookup without storing the raw secret.
- The stored key hash is HMAC-SHA-256 of the full raw API key using the server-side secret.
- Missing or invalid API keys return `401`.

Current implementation status: Implemented with API-key generator, hasher, validator, request context, authentication filter, key metadata model, repository access, audit events, and backend tests.

### 5. Scope Authorization With `@RequiresScope`

Purpose: Enforce least-privilege access on protected endpoints after API-key authentication succeeds.

User benefit: A client can be granted only the endpoint access it needs, such as aircraft read access without broader access to other domains.

Endpoint and security impact:

- Protected endpoints declare required scopes using `@RequiresScope`.
- Supported scopes are `read:aircraft`, `read:maintenance`, `read:pairs`, and `read:usage`.
- Valid API keys without the required scope return `403`.
- Missing or invalid API keys return `401`.

Current implementation status: Implemented with the `@RequiresScope` annotation, scope enforcement interceptor, API-key scope repository, authenticated request context, and a protected reference endpoint test path.

### 6. Key Lifecycle Management

Purpose: Support operational control after a key is issued, including revocation, rotation, and expiration.

User benefit: Admins can respond to lost keys, access changes, and normal credential rotation without changing the overall client registration model.

Endpoint and security impact:

- Admin JSON and UI routes support revoking issued keys.
- Rotation creates a replacement claim invitation instead of directly returning a new raw key.
- Expired and revoked keys must not validate.
- Expired claim invitations cannot be claimed.

Current implementation status: Revocation, rotation initiation, expiration checks, lifecycle statuses, admin UI revocation flow, and tests are implemented. Production scheduling and operational policies can be refined separately.

### 7. Audit And Security Observability

Purpose: Record security-sensitive lifecycle and authentication events without exposing secrets.

User benefit: Security and operations teams can review who created clients, issued invitations, completed claims, revoked keys, and triggered failed authentication or claim attempts.

Endpoint and security impact:

- Audit events avoid raw API keys, raw claim codes, HMAC hashes, and BCrypt hashes.
- Authentication failures and claim failures can be investigated without leaking submitted secrets.
- Admin and claim workflows include audit records for important lifecycle events.

Current implementation status: Implemented with audit event model, repository, service, event types, and integration in client, claim, validation, revocation, and rotation workflows.

### 8. Admin And Claim Qute UI

Purpose: Provide simple server-rendered screens for internal admins and client-side claim users without adding a frontend build system.

User benefit: Admins can manage clients, invitations, keys, and revocation from browser pages. Client-side admins can complete the claim flow without using raw JSON.

Endpoint and security impact:

- Admin UI routes are under `/admin/ui/...` and use the temporary dev/test admin guard.
- Claim UI routes are under `/key-claim/ui...` and are public so approved users can complete a claim.
- Raw claim codes and raw API keys are shown only in the allowed one-time views.
- Secrets are not placed in URLs.

Current implementation status: Implemented with Quarkus Qute templates, static CSS, admin screens, claim screens, and UI resources that call services rather than repositories directly.
