# API Key Management Workflows

## 1. Purpose

The API key management feature manages API access for consuming applications. It gives approved clients a controlled way to call FMT REST APIs without requiring direct database access.

API keys provide scoped, auditable access to API endpoints. Each key is associated with an API client, explicit scopes, lifecycle metadata, and security audit events so access can be granted, reviewed, revoked, rotated, and expired.

## 2. Actors

- Internal admin: Creates API clients, creates claim invitations, revokes keys, and initiates rotation.
- Client-side admin: Receives a claim code through an internal out-of-band process and completes the claim workflow.
- Client application: Calls protected API endpoints using an issued API key.
- API runtime/filter: Authenticates API keys from requests and makes key, client, and scope information available for authorization.
- Future SSO/Windows AD admin auth: Final admin authentication mechanism for admin endpoints. The current dev admin guard is temporary and must not be treated as production admin auth.

## 3. Core Concepts

- API client: A registered consuming application or organization that owns API keys.
- Claim invitation/request: An admin-approved invitation allowing a client-side admin to claim one API key.
- Claim identifier / approved email: A username-like approved value used to match the claim attempt to the invitation.
- Claim code: A one-time secret generated for a claim invitation and manually delivered out-of-band.
- API key: The raw credential used by a client application in API requests after a successful claim.
- Key prefix: The non-secret lookup prefix stored with the key, for example `ak_prod_N7F3K92A`.
- Scopes: Permission strings such as `read:aircraft`, `read:maintenance`, `read:pairs`, and `read:usage`.
- Audit events: Security records for sensitive lifecycle and authentication events.

## 4. Important Rule About Email

The approved email field is only a claim identifier or username-like value.

This system does not send email. It does not use SMTP, magic links, email verification, password reset links, claim links, or notification delivery. The claim code is generated by the system and manually delivered out-of-band by an internal/admin process.

## 5. Workflow: Create API Client

1. Internal admin creates an API client with client name, contact/claim identifier information, and owner metadata.
2. System stores the API client with an active status.
3. System records a client-created audit event.
4. The API client can later be enabled, disabled, listed, and viewed by admin workflows.

## 6. Workflow: Create Claim Invitation

1. Internal admin chooses the API client.
2. Internal admin provides the claim identifier, key name, scopes, environment, expiration, and approval reference.
3. System validates that the API client is active and the requested scopes are allowed.
4. System generates a one-time claim code.
5. System stores only a BCrypt hash of the claim code.
6. System persists the approved scopes with the claim invitation.
7. System returns the raw claim code only in the claim-invitation-created response.
8. System records an invitation-created audit event without the raw claim code or BCrypt hash.

## 7. Workflow: Claim API Key

1. Client-side admin enters the claim identifier and claim code.
2. System finds the matching claim invitation.
3. System rejects invitations that are expired, locked, revoked, already claimed, or otherwise not pending.
4. System verifies the submitted claim code against the stored BCrypt hash.
5. Wrong claim codes increment failed attempts and lock the invitation after the configured maximum.
6. System generates an API key only after successful claim validation.
7. System stores only the key prefix and HMAC-SHA-256 hash of the full raw API key.
8. System creates API key scope rows from the persisted invitation scopes.
9. System marks the invitation as claimed.
10. System returns the raw API key only in the claim response.
11. System records claim/key-created audit events without raw secrets or hashes.

## 8. Workflow: Runtime API Authentication

1. Client application sends `X-API-Key: <full-api-key>`.
2. API runtime/filter extracts the key prefix from the submitted key.
3. System looks up the stored key by prefix.
4. System rejects missing, malformed, unknown, revoked, expired, or invalid keys.
5. System rejects keys belonging to disabled clients.
6. System verifies the submitted raw key by computing HMAC-SHA-256 with the server-side secret and using constant-time comparison against the stored hash.
7. On success, system makes authenticated key, client, environment, and scope information available to later authorization logic.
8. System may update `lastUsedAt` on successful validation.

## 9. Workflow: Scope Authorization

Protected API endpoints declare required scopes with `@RequiresScope`.

Requests with a missing, malformed, unknown, expired, revoked, or hash-invalid API key return `401`. Requests with a valid API key that lacks the required scope return `403`. API keys must never authorize admin endpoints.

## 10. Workflow: Revoke Key

1. Internal admin selects an API key to revoke.
2. System sets key status to `REVOKED`.
3. System records revocation metadata such as revoked time, actor, and reason when supported by the model.
4. System records a key-revoked audit event.
5. Revoked keys must not validate on future API requests.

## 11. Workflow: Rotate Key

1. Internal admin initiates rotation for an existing key.
2. System creates a replacement claim invitation for the same client, environment, and scopes.
3. System records rotation metadata on the old key when supported by the model.
4. System records a rotation-initiated audit event.
5. Rotation does not directly return a new raw API key.
6. The replacement raw API key is created only after the replacement claim invitation is successfully claimed.

## 12. Workflow: Expiration

Claim invitations expire at their configured expiration time. Expired invitations cannot be claimed and should be marked `EXPIRED`.

API keys expire at their configured expiration time. Expired keys must not validate and should be marked `EXPIRED`.

Scheduled maintenance may periodically mark expired invitations and keys. Cleanup must not expose or persist raw secrets.

## 13. Workflow: Audit

Record security-sensitive events, including:

- Client created
- Client enabled
- Client disabled
- Claim invitation created
- Claim failed
- Claim completed
- Key created
- Key validated when appropriate
- Key revoked
- Key rotation initiated

Audit records must not include raw API keys, raw claim codes, HMAC hashes, BCrypt hashes, or any other raw secret material.

## 14. State Transitions

Claim invitation states:

- `PENDING`: Invitation is available for claim.
- `CLAIMED`: Invitation was successfully used and cannot be reused.
- `EXPIRED`: Invitation expired before successful claim.
- `LOCKED`: Invitation exceeded failed claim-code attempts.
- `REVOKED`: Invitation was administratively revoked.

API key states:

- `ACTIVE`: Key can validate if unexpired and client is active.
- `REVOKED`: Key was administratively revoked and cannot validate.
- `EXPIRED`: Key exceeded its expiration and cannot validate.
- `ROTATED`: Key has been superseded by rotation metadata and must not validate after any supported grace period.

## 15. Security Invariants

- Raw API keys are never stored.
- Raw claim codes are never stored.
- Raw secrets are never logged.
- Raw secrets are never audited.
- HMAC hashes are stored only in API key hash fields.
- BCrypt hashes are stored only in claim-code hash fields.
- API keys cannot access admin endpoints.
- Admin authentication will later be SSO/Windows AD.
- The dev admin guard is temporary and must not be used as production admin authentication.
